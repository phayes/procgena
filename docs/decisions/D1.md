# D1: crate names, YAML crate, `Ground` coordinates

Decision brief for gate D1 in [ROADMAP.md](../../ROADMAP.md). D1 blocks F1
(names, coordinates) and F3 (YAML crate). Research only: nothing in the
code or in `Cargo.toml` changes until the user decides.

Researched 2026-11-23 against `master` at `89edd32`.

## Decisions (user, 2026-11-23)

The user took every recommendation below:

1. Core crate: **`procgena_core`**, in `core/crates/procgena_core/`.
2. Shared Bevy crate: **`procgena_core_bevy`**, in
   `core/crates/procgena_core_bevy/`, **created in R1** with its first
   content, not empty in F1.
3. `procgena_mesh` moves to **`specimen/crates/procgena_specimen/`**.
4. Layering A: **`procgena_specimen` depends on `procgena_core`**, and the
   core crate depends on glam alone. `HeightGrid::from_object` becomes
   `Specimen::height_grid(level, filter, cell) -> Option<HeightGrid>`.
5. YAML crate: **`serde-saphyr`, pinned to `"2.2"`**, added in F3 (not
   before). `strict_booleans` stays off, so `bool` fields accept `yes` and
   `no`, and string fields never turn into booleans.
6. `Ground` takes **World `f64` positions** and returns `f32` heights and
   gradients. Scatters work chunk-local inside and convert at the call.
7. `Ground` has `height(DVec2) -> f32`, `gradient(DVec2) -> Vec2` (default:
   central differences) and `sample(DVec2) -> GroundSample` (default: both),
   and is `Send + Sync`.
8. `HeightGrid`'s gradient uses central differences one cell apart.
9. `ChunkFrame` lands in C2, not F1.
10. F1 moves only stone's and clump's identical random-number code into
    the core crate. F2 moves tree's, deadwood's and mushroom's, since it
    changes their outputs anyway.

## 1. Names of the two shared crates

### What the crates hold

From ARCHITECTURE.md, "Where shared code lives":

- **Engine-free core crate:** the rules. Content hash, seeds and ids, the
  specimen budget, the LOD type, `Ground`, the `Scatter` trait, shared
  placement, masks, edits and queries. F1 puts the shared hashing and
  random numbers there first, then `Ground`, `FlatGround` and `HeightGrid`.
- **Shared Bevy crate:** the shared runtime. The instanced renderer, the
  dither shader, the shared cache, wind, texture loading, promotion.

Constraints on the names:

- The studio binary is already `procgena`, so neither can be called that.
- Every other pair in the workspace is `procgena_<x>` plus
  `procgena_<x>_bevy` (stone, tree, clump, deadwood, mushroom). The rule
  "Engine-free core, thin Bevy crate" in ARCHITECTURE.md names this split
  for every level.
- None of the candidates below is taken on crates.io (checked 2026-11-23;
  `procgena` and `procgena_mesh` are not published either), so nothing
  blocks publishing later.

### Core crate

| Name | For | Against |
|------|-----|---------|
| **`procgena_core`** | The name ARCHITECTURE.md already uses in prose ("the core crate"), so the documents need the fewest edits. Says "everything else builds on this", which is true: every generator, the terrain (once it implements `Ground`) and every level above will depend on it. A common Rust pattern (`bevy_core` in older Bevy, `tokio-core`). | "Core" invites a dumping ground. Needs a rule in its crate docs of what belongs there (the list above) and what does not (anything about one specimen's shape goes in `procgena_specimen`). |
| `procgena_common` | Honest about being shared. | Reads like a bag of helpers, not the home of the `Scatter` trait and the World's rules. Same dumping-ground risk, with less sense of being the base. |
| `procgena_rules` | Matches ARCHITECTURE.md's own word ("the rules"). | Unusual; at a call site `procgena_rules::Ground` and `procgena_rules::SpecimenId` read oddly. Easily confused with Biome rules (Ecotope rules matched on terrain labels). |
| `procgena_scatter` | Most of what it will hold is about placing copies (Ground, masks, placement, Scatter trait). | Wrong for the content hash, seeds, LOD type and edits, which every level uses. Clashes with the level name: `TreeScatter` would not live in `procgena_scatter`. |

### Bevy crate

| Name | For | Against |
|------|-----|---------|
| **`procgena_core_bevy`** | Follows the house pattern exactly: `procgena_core` and its thin Bevy crate. The CLAUDE.md table, tooling and agents can rely on "`<x>_bevy` is the Bevy half of `<x>`" without an exception. | Longer, and "core bevy" sounds odd in prose. Its contents (renderer, wind, textures) are more than a thin layer over `procgena_core`. |
| `procgena_bevy` | Short, and reads naturally as "procgena's shared Bevy runtime". Matches common ecosystem naming (`bevy_<thing>`, `<thing>_bevy`). | Breaks the pattern: the one Bevy crate with no core of the same name. Reads like a facade plugin for all of procgena, which it is not (each asset still has its own Bevy crate). If a facade crate is ever wanted, this is the name it would want. |
| `procgena_runtime` | Says what it is for. | Hides that it is Bevy; nothing else in the workspace names an engine role this way. |
| `procgena_render` | Short. | Too narrow: wind, promotion, cache and texture loading are not rendering. |

### Folder layout

Following today's layout (`<area>/crates/<package>`):

- `core/crates/procgena_core/` and `core/crates/procgena_core_bevy/`.
- `mesh/crates/procgena_mesh/` moves to
  `specimen/crates/procgena_specimen/`.

A top-level folder called `core` is fine for cargo (only the crate name
`core` is reserved, not a folder), but `shared/` is an alternative if the
user prefers to avoid the word on disk.

### Which crate depends on which

The documents disagree here, and F1 has to pick:

- ARCHITECTURE.md, "Naming", lists `SpecimenId` and
  `HeightGrid::from_specimen` under `procgena_specimen`.
- ARCHITECTURE.md, "Where shared code lives", puts "content hash, seeds and
  ids", the LOD type and `Ground` (so `HeightGrid`) in the core crate.

Rust allows inherent methods only in the crate that owns the type, so
`HeightGrid::from_specimen` needs the core crate to depend on
`procgena_specimen`, while `SpecimenId` hashing and the LOD type in
specimens' levels want the opposite.

| Layering | For | Against |
|----------|-----|---------|
| **A. Core at the bottom** (`procgena_specimen` → `procgena_core` → glam) | The core crate stays tiny: the terrain, plant's future core crate, the Ecotope, Biome and World crates can depend on it without meshes and tags. `SpecimenId`, the hash and the LOD type live with the rules, and a specimen can carry them. | `HeightGrid::from_specimen` cannot exist; it becomes `Specimen::height_grid(level, filter, cell) -> Option<HeightGrid>` in `procgena_specimen`. ARCHITECTURE.md's naming table changes by one row. |
| B. Specimen at the bottom (`procgena_core` → `procgena_specimen`) | `HeightGrid::from_specimen` keeps its planned name. | Everything that needs `Ground` (the terrain) pulls in meshes and tags. `SpecimenId` must be a bare newtype in `procgena_specimen` with its hashing in the core crate, splitting one idea across two crates. |

**Recommendation: A.** Either way every generator depends on both, so
build times are about the same; A keeps the bottom of the graph small.

### When to create the Bevy crate

The TODO "Shared crates" says to create both in F1, but nothing moves into
the Bevy crate until R1 (LOD and dither) and R2 (renderer). An empty crate
costs little, but `cargo machete` and the docs would carry a placeholder.
**Recommendation:** settle the name now, create the crate in R1 with its
first content. F1 then only creates `procgena_core`.

## 2. YAML crate

### What rule 10 needs

- Reading files people wrote by hand, with comments: clear errors with
  line and column, and no surprises such as `no` read as `false` in a
  string field.
- Writing presets back out from the studio (serialize).
- A `base` preset plus only what differs. procgena does this itself today:
  tree's `merge_json` (`tree/crates/procgena_tree/src/options.rs`) merges
  `serde_json::Value`s. So the crate needs to deserialize into
  `serde_json::Value` (or its own `Value`), and YAML anchors and merge keys
  (`<<: *base`) are a nice extra inside one file, not a requirement.
- Licence in `deny.toml`'s allow list, no RustSec advisory that
  `cargo deny check` would fail on, and an MSRV at or below 1.97.1
  (plant's MSRV check).

### Notes per crate

- **serde-saphyr.** The most used of the active crates, pure safe Rust,
  fuzz-tested, and passes the YAML Test Suite. Rejects duplicate keys by
  default, expands merge keys by default (explicit keys override merged
  ones), and limits alias expansion (50 000 aliases, depth 64), so a
  "billion laughs" file can't hang the studio. Errors show the source
  snippet. A `Commented<T>` wrapper can read and write comments, which no
  other serde crate here offers. Catches:
  - **No `Value` type of its own.** It deserializes straight into our types
    or into `serde_json::Value`, which is what `merge_json` uses anyway.
  - **One owner, fast major versions:** 1.0 in July 2026, 2.0 in October,
    3.0-rc in November, and 3.0 changes how some YAML is read. Pin `"2.2"`
    and upgrade on purpose.
  - **Lenient booleans by default:** `yes`, `no`, `on` and `off` are read
    as booleans when the field is a `bool` (`strict_booleans` is off). This
    only applies to `bool` fields, so a string field never turns into
    `false`; set `strict_booleans` if the user wants YAML 1.2 only. On
    writing, strings such as `no` are quoted.
- **yaml_serde.** The YAML organisation's fork of serde_yaml, with the
  same API (`Value`, `Mapping`, `from_str`), so it is the least work to
  adopt and the most familiar. But it is still C translated to unsafe
  Rust, merge keys need an explicit `apply_merge()`, there have been no
  commits in the last three months, and recent issues are unanswered
  (an alias pointing at the wrong node when an anchor name is reused;
  integer overflow on large input).
- **noyalib.** Technically strong (pure Rust, `Value`, a lossless editor
  that keeps comments), but under its 0.0.x scheme every patch release
  may break the API, and it shipped 60 in six months. It has already had
  one advisory.
- **serde_yml.** Deprecated by its author. RUSTSEC-2025-0068 matches every
  version, so `cargo deny check` would fail unless it is ignored. Do not
  use.
- **serde_yaml_ng, serde_norway, serde_yaml_bw, serde_yaml2.** Dormant,
  or (serde_yaml_bw) replaced by serde-saphyr by the same author. The
  libyaml-based ones carry the unmaintained `unsafe-libyaml` or its fork.

### Recommendation

**serde-saphyr, pinned to `"2.2"`**: maintained, safe, merge keys and
alias limits on by default, licences and MSRV fit. **yaml_serde** is the
fallback if the user prefers serde_yaml's exact API and a `Value` type over
pure Rust. The choice is the user's; nothing is added to `Cargo.toml`
before F3.

## 3. `Ground` coordinates (open question 8)

### Today

- `procgena_mesh::Ground::height(&self, x: f32, z: f32) -> f32`, with
  impls for `FlatGround`, any `Fn(f32, f32) -> f32`, and `HeightGrid`
  (`f32` origin and cell). No `Sync` bound.
- Callers: tree's `GrovePlacement::new` (`&dyn Ground`; samples the trunk
  and eight points around it, then `atan(steepest / footprint)` against
  `max_slope`), deadwood's `StickScatter::new` (`&dyn Ground`; fits a plane
  to the contacts and two side points), `procgena_tree_bevy` and
  `procgena_deadwood_bevy` (flat ground or a `HeightGrid` from the host's
  object), the studio's grove tab (`FlatGround`), and the examples and tests
  of tree, deadwood, clump and impostor. Plant uses its own `PlantGround`
  (flat, heightmap image or mesh); stone, mushroom and clump place on hosts,
  not on `Ground`.
- The terrain does **not** use `Ground`. It has its own
  `HeightField: Sync { fn height(&self, p: DVec2) -> f32 }`, implemented by
  `Terrain` and `TerrainGenerator`, and `HeightTile` samples it on a lattice
  with an `I64Vec2` origin and an `f64` step.
- The terrain's design ([terrain/plan.md](../../terrain/plan.md), "Coordinates
  and determinism"): World positions in the API are `DVec2` (`f64`
  metres); inside, a position becomes an `i64` lattice index plus an `f32`
  fraction (see `noise::gradient_noise`); heights are `f32`; mesh vertices
  will be `f32` relative to their chunk's integer origin. Its test plan
  repeats the tests at `x = 10^7 m`.
- The terrain's gradients are already `Vec2` (`f32`): `relief.gradient`
  takes central differences 0.5 m apart, and the seam offers carry a
  `gradient: Vec2`.

### Precision

Spacing between neighbouring representable values (one ulp):

| Distance from origin | `f32` | `f64` |
|---|---|---|
| 64 m (one chunk) | 7.6 µm | ≈ 1.4·10⁻¹⁴ m |
| 1 km | 61 µm | ≈ 1.1·10⁻¹³ m |
| 10 km | 0.98 mm | ≈ 1.8·10⁻¹² m |
| 100 km | 7.8 mm | ≈ 1.5·10⁻¹¹ m |
| 1 000 km | 6.25 cm | ≈ 1.2·10⁻¹⁰ m |
| **10⁷ m** | **1 m** | **≈ 1.9·10⁻⁹ m** |

What breaks with `f32` World positions at 10⁷ m:

- Tree's footing samples sit `footprint` (0.1–1 m) from the trunk. At 1 m
  spacing they round onto the trunk or a metre away, so `steepest /
  footprint` is noise and the slope test is meaningless.
- A central-difference gradient with a 0.5 m step cannot even be formed.
- Noise inputs, lattice cells and copy ids computed from `f32` positions
  snap to the metre, so placement and the terrain disagree.
- Even at 10 km, millimetre steps are visible as jitter on a 0.5 m step
  and on per-copy transforms.

`f32` is fine **inside a chunk**: 64 m chunks resolve to 7.6 µm, and the
coarsest chunk levels (64 m doubled a few times) stay well under a
millimetre. Heights are `f32` everywhere and stay so: even 9 km up, an
`f32` height resolves to under a millimetre, and gradients are ratios near
0 to 10.

### What the GPU wants

- WGSL has no `f64` in WebGPU. wgpu's `SHADER_F64` is native-only (not
  Metal, not the web) and runs at a small fraction of `f32` speed on
  consumer GPUs (1/64 on recent NVIDIA consumer cards). Every shader in the workspace is
  `f32`, and the plant web demo runs on WebGPU.
- Bevy's `Transform` and `GlobalTransform` are `f32`, and Bevy has no
  built-in large-world coordinates. Large worlds in Bevy use a floating
  origin or integer grid cells plus `f32` offsets (the `big_space` crate's
  approach). That choice belongs to S1 (streaming), not D1.
- So on the GPU everything is chunk-local `f32`: instance buffers hold
  transforms relative to a chunk origin, and a GPU Scatter reads the ground
  as a height and gradient texture per tile (ARCHITECTURE.md, "Ground
  carries slope"), indexed from the tile's integer origin like `HeightTile`.

This is true whichever way the CPU trait goes. The question is only what
the CPU `Ground` call takes.

### The two options

**Option L: chunk-local `f32`.** `height(&self, x: f32, z: f32)` relative
to some chunk origin.

- The ground has to know which chunk's origin the caller means. Either
  every Scatter gets a wrapper (`ChunkGround { ground, origin }`) per
  chunk, or the origin is a trait argument, which is option W in disguise.
- Scatters use the same chunk grid **at different levels** ("One grid,
  driven by requests" in ARCHITECTURE.md): grass on 64 m chunks, trees on
  much coarser ones. Their local frames differ, so anything passed between
  them (masks, edits, queries) needs a frame conversion at every hand-off.
  A mix-up is silent: right at the origin chunk, wrong everywhere else.
- A user's own `Ground` has to handle the origin correctly or it is wrong
  away from the origin, with no type to catch it.
- The terrain, which already takes `DVec2`, needs an adapter.

**Option W: World `f64`.** `height(&self, p: DVec2)`.

- One `Ground` serves every chunk at every level with no wrapper; the
  terrain implements it as it stands (`HeightField` and `Ground` become the
  same trait in G2).
- Frame-free hand-offs: masks, edits, queries and copy ids talk World
  positions, and only buffers and shaders are chunk-local.
- Matches the terrain's own rule: `f64` at the API, integer lattice plus
  `f32` fraction inside.
- Cost per call: two `f64` additions to turn a chunk-local point into a
  World point (`chunk_origin + local.as_dvec2()`), against a terrain call
  that runs relief, border bending and carving. Negligible. `f64` scalar
  maths runs at about the same speed as `f32` on the CPU; only SIMD
  batches halve, and a Scatter's inner loop stays `f32`.

### Cost for each Scatter (option W)

Each Scatter keeps its maths chunk-local in `f32` (spots, jitter,
footprints, transforms), and converts only at the `Ground` call and when
it computes World lattice cells. The core crate gives one small helper so
this is written once:

```rust
/// A chunk's frame: World origin in f64, everything inside in f32.
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct ChunkFrame {
    pub origin: DVec2,
}

impl ChunkFrame {
    pub fn to_world(self, local: Vec2) -> DVec2 { self.origin + local.as_dvec2() }
    pub fn to_local(self, world: DVec2) -> Vec2 { (world - self.origin).as_vec2() }
}
```

In F1 itself, today's Scatters (grove, sticks) still place around their own
centre, so their frame is the World origin and each call site only wraps
its point: `ground.height(DVec2::new(x.into(), z.into()))`. World-anchored
lattices and chunk frames arrive with C2.

### Proposed signature for F1

```rust
use glam::{DVec2, Vec2, Vec3};

/// Central-difference step used by the default `gradient`, in metres.
/// The same as the terrain's relief step, so the two agree.
pub const GRADIENT_STEP: f64 = 0.5;

/// The ground under a point: its height and its rate of change.
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct GroundSample {
    /// Height in metres, NaN where there is no ground.
    pub height: f32,
    /// dh/dx and dh/dz (metres per metre). NaN where the ground can't say.
    pub gradient: Vec2,
}

impl GroundSample {
    /// The upward unit normal, `normalize(-dh/dx, 1, -dh/dz)`.
    pub fn normal(&self) -> Vec3;
    /// The steepest slope at this point, in degrees from 0 to 90.
    pub fn slope_degrees(&self) -> f32;
}

/// The shape of the ground: a height at each World position in X and Z,
/// with Y up.
pub trait Ground: Send + Sync {
    /// Height in metres at World position `p` (`x`, `z`), or NaN where
    /// there is no ground.
    fn height(&self, p: DVec2) -> f32;

    /// Rate of height change along X and Z at `p`. The default takes
    /// central differences of `height`, `GRADIENT_STEP` apart, and is NaN
    /// if any of the four heights is.
    fn gradient(&self, p: DVec2) -> Vec2 { /* central differences */ }

    /// Height and gradient together. Grounds that work out both in one
    /// pass (the terrain) override this; callers that need both use it.
    fn sample(&self, p: DVec2) -> GroundSample {
        GroundSample { height: self.height(p), gradient: self.gradient(p) }
    }
}

impl Ground for FlatGround { /* height 0, gradient ZERO */ }
impl<F: Fn(DVec2) -> f32 + Send + Sync> Ground for F { /* height only */ }
impl Ground for HeightGrid { /* gradient from its own cells */ }
```

Choices made in it:

- **Gradient, not normal.** The terrain already speaks gradients (`Vec2`
  in seam offers, `relief.gradient`), the Biome's slope labels are a
  function of the gradient, and the normal and slope angle follow from it
  (`GroundSample::normal`, `slope_degrees`). A gradient of NaN at a missing
  sample is easier to test than a normal.
- **`sample` is in from the start.** The terrain's analytic chain rule
  gives height and gradient in one pass, and placement nearly always wants
  both, so asking twice would run the terrain stack twice. A defaulted
  method can be added later without breaking implementors, so this can
  wait if the user prefers the smallest trait; but C1's Scatters would
  then be written against `height` plus `gradient` and need a second pass.
- **`Send + Sync`.** The terrain's `HeightField` is already `Sync`,
  placement runs on rayon, and Bevy tasks need `Send` to hold an
  `Arc<dyn Ground>`. Closures that capture `Rc` or `RefCell` stop being
  grounds; none of the call sites listed under "Today" use one.
- **Closures take `DVec2`.** One convention with the terrain. Tests write
  `|p: DVec2| 0.5 * p.x as f32` instead of `|x, _z| 0.5 * x`.
- **`HeightGrid`** keeps `f32` heights, but its origin becomes `DVec2` and
  its cell `f64`; `from_fn(min: DVec2, max: DVec2, cell: f64, height: impl
  Fn(DVec2) -> f32)`. Its gradient comes from the bilinear patch it already
  blends (exact for its own surface, but steps at cell edges), or from
  central differences one cell apart (smooth, but blurs one cell). Either
  is fine for F1; see the questions.
- **Masks are not in this decision.** Density functions are
  `Fn(f32, f32) -> f32` today; how masks live is D2. If they stay
  functions of position, they should take `DVec2` for the same reasons.

## 4. What F1 then does

**New crate `procgena_core`** (`core/crates/procgena_core/`):

- `Cargo.toml` (glam only; serde comes with later milestones),
  `src/lib.rs`.
- `src/hash.rs`, `src/rng.rs`: one hashing and random-number module, made
  from stone's `src/hash.rs` and clump's copy of it
  (`clump/crates/procgena_clump/src/hash.rs`). Tree, deadwood and mushroom

  `HeightGrid`.

## Questions for the user

1. **Core crate name:** `procgena_core` (recommended), `procgena_common`,
   `procgena_rules` or `procgena_scatter`?
2. **Bevy crate name:** `procgena_core_bevy` (recommended, keeps the
   `<x>_bevy` pattern) or `procgena_bevy` (shorter, breaks it)?
3. **Folder:** `core/crates/...` or `shared/crates/...`? And
   `specimen/crates/procgena_specimen`?
4. **Layering:** core at the bottom, so `HeightGrid::from_object` becomes
   `Specimen::height_grid` (recommended), or specimen at the bottom so
   `HeightGrid::from_specimen` keeps its planned name?
5. **Create the Bevy crate in F1, empty, or in R1 with its first content**
   (recommended)?
6. **YAML crate:** `serde-saphyr` 2.2 (recommended: pure Rust,
   maintained, merge keys) or `yaml_serde` (serde_yaml's API and `Value`,
   unsafe C translation)? And should booleans be strict YAML 1.2
   (`strict_booleans`), or accept `yes`/`no` in `bool` fields?
7. **Coordinates:** World `f64` in, `f32` out (recommended), or
   chunk-local `f32`?
8. **`sample` in F1** (recommended), or only `height` and `gradient`?
9. **`Send + Sync` on `Ground`** (recommended), or `Sync` only like the
   terrain's `HeightField`?
10. **`HeightGrid`'s gradient:** from its bilinear patch (exact for the
    grid, steps at cell edges) or central differences one cell apart
    (smooth)? Recommendation: central differences, so a grid sampled from
    the terrain gives the same slope test as the terrain to within a cell.
11. **`ChunkFrame` in F1 or C2?** Recommendation: C2, where chunked
    placement starts; F1 has no chunks yet.
12. **Tree, deadwood and mushroom's own `rng.rs`:** move them into the core
    crate in F1 where outputs stay bit-identical, or leave them for F2's
    "variants seeded by one shared function"? Recommendation: F1 moves
    stone's and clump's (identical copies) only; F2 does the rest, since
    it changes their outputs anyway.

On settling, update ARCHITECTURE.md: the crate names, "Decisions to make"
(names and YAML crate), open question 8, and the naming table if layering
A is chosen.
