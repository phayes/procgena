# C1: the same inputs for every Scatter

Roadmap milestone C1. This file is for the lane workers (tree, deadwood,
mushroom, stone). It records the input shape every Scatter takes and the
answer to open question 3. The coordinator approved it on 2026-11-23, with
the changes folded in below. C2 (the `Scatter` trait, masks out, integer
World-lattice placement, `K_d`) is out of scope.

## Decisions

1. **One input type, `procgena_core::scatter::ScatterInput`.** It holds the
   ground, an optional mask, the area and the seed. Every Scatter in a core
   crate takes it.
2. **The area is anchored at its centre.** `ScatterArea` is a World centre
   plus a size. A corner anchor would move every tree when the size
   changes, which `tree/tests/grove.rs::growing_the_size_keeps_the_trees_already_there`
   forbids.
3. **The seed is a `u32`**, matching `Rng::new` and `derive_seed`. Later it
   takes whatever F2's `child_seed` returns. F2 may bring in a seed newtype,
   so the field is a single plain field that is easy to switch.
4. **The slope limit is a Scatter option, not an input and not an asset
   option.** It stays in each Scatter's options (`max_slope`, in degrees),
   so it never enters an asset's options hash or `SpecimenId`. What every
   Scatter shares is one check (`steeper_than`) and the order of the
   checks.
5. **Open question 3: placement is declarative, and the Scatter carries it
   out.** The asset never sees the `Ground`. Each asset declares a
   `Placement`, a Scatter may override it, and one executor, `place()`,
   puts every piece down (approved by the user; it replaced the first
   design, `settle()`).
6. **No renames in C1.** Existing types keep their names (`TreeGrove`,
   `GrovePlacement`, `StickScatter`, `MushroomScatter`) and take the new
   input. The renames happen in F3.
7. **Groups of members** (fairy rings, tufts, pebble clusters): decided by
   the user with Addresses (D3 §7b, "Decisions"). How a group is handled
   depends on who defines it; see "Groups" below.

Plant is out of C1 and unchanged. It is a Bevy component placed on the GPU,
with no seed, and joins at R3 and C3.

## The shared types (`procgena_core::scatter`)

```rust
/// A rectangle of World ground to scatter over, around a centre.
pub struct ScatterArea { pub centre: DVec2, pub size: Vec2 }
impl ScatterArea {
    pub fn new(centre: DVec2, size: Vec2) -> Self;
    pub fn world(&self, local: Vec2) -> DVec2;    // centre + local
    pub fn contains(&self, local: Vec2) -> bool;  // |local| <= size / 2 on both axes
}

/// How much of a Scatter's density is allowed at a World position, from
/// 0 to 1. A density multiplier only: hard exclusion (nothing inside a
/// trunk) is C2's exact disc tests. Closures `Fn(DVec2) -> f32 + Send + Sync`
/// are masks.
pub trait Mask: Send + Sync { fn density(&self, p: DVec2) -> f32; }

/// What every Scatter gets from the level above it.
#[derive(Clone, Copy)]
pub struct ScatterInput<'a> {
    pub ground: &'a dyn Ground,
    pub mask: Option<&'a dyn Mask>,   // None = full density everywhere
    pub area: ScatterArea,
    pub seed: u32,
}
impl<'a> ScatterInput<'a> {
    pub fn new(ground: &'a dyn Ground, area: ScatterArea, seed: u32) -> Self;
    pub fn with_mask(self, mask: &'a dyn Mask) -> Self;
    pub fn density(&self, local: Vec2) -> f32;     // clamped to 0..=1; 1 without a mask
    pub fn sample(&self, local: Vec2) -> GroundSample;
}

/// Whether the ground at `s` is steeper than `max_degrees`. 90 or more
/// never rejects a measured slope. A NaN gradient counts as too steep.
/// (Ground::gradient's default and HeightGrid compare the side that has
/// ground with the point itself where the other side has none, so a grid
/// that exactly covers the area has a slope up to its edge.)
pub fn steeper_than(s: &GroundSample, max_degrees: f32) -> bool;

/// How a piece stands on uneven ground (see "Open question 3").
pub struct Placement { pub conform: f32, pub rest: Rest, pub embed: f32, pub max_bend: Option<f32> }
pub enum Rest { Lowest, Plane }
/// Where a piece touches flat ground, and its size.
pub struct Footprint { pub contacts: Vec<Vec3>, pub extra: Vec<Vec2>, pub size: f32 }
/// Puts a piece down as `placement` says.
pub fn place(ground: &dyn Ground, at: DVec2, yaw: f32, footprint: &Footprint,
             placement: &Placement) -> Option<Placed>;
```

The exact signatures are in the code; this sketch shows the shape.

### How a Scatter uses it

- **Constructor:** `X::new(&options, &input) -> Result<X, XError>`, for
  example `GrovePlacement::new(&grove, &input)` (tree lane),
  `StickScatter::new(&options, &input)` (deadwood lane),
  `MushroomScatter::new(&mushroom, &options, &input)` on the ground
  (mushroom lane; `on(host)` stays until `MushroomGrowth`), and
  `StoneScatter::new(&options, &input)` (stone).
- **Positions out** are `f32`, relative to `area.centre`. A Bevy crate puts
  the Scatter's parent entity at the centre. Ground and mask are always
  asked at `area.world(local)`. Each Scatter keeps its float lattice
  anchored to the centre. World-anchored lattices come in C2.
- **Size** moves out of each Scatter's options and into the area.
- **Seed:** the Scatter uses only `input.seed`. Options keep their `seed`
  field in C1, as the value that viewers and the studio pass when a Scatter
  is built on its own. F3 renames it to `default_seed`. The copies are
  seeded from `input.seed`. A variant (specimen) in a Scatter is seeded
  by `SpecimenId { world_seed: input.seed, pool, slot }.seed()`; an asset
  built on its own uses its options' seed, cached by `(PoolId, seed)`.
  Stone does this (`StoneOptions::variant`, `StonePool::world_seed`).
- **Order of checks** (TODO "Scatters use it"):
  1. the mask and density;
  2. `steeper_than(&input.sample(p), max_slope)`, from one `Ground::sample`;
  3. only then, footprint sampling and `place()`.

## Open question 3: placement is declarative, the asset never sees the Ground

A specimen is built once, in its own space and on flat ground, and many
copies share it anywhere in the World (see the specimen budget, and
impostors keyed by `SpecimenId`). An asset that read the Ground at build
time would make every copy a unique mesh.

So each asset declares how it stands, as a `Placement`, and the Scatter
carries it out with one executor, `place()`. A Scatter may override the
asset's `Placement` per class or species (an `Option<Placement>`). The
slope limit stays a Scatter option. Placement is not part of any options
hash or `SpecimenId`: it moves copies, it doesn't change shapes.

`Placement`'s fields (serde behind core's `serde` feature, all with
defaults):

- `conform`, from 0 to 1: 0 keeps the piece upright (trees, mushrooms,
  stumps), 1 lies it along the ground (logs), and values between tilt it
  partway (a slerp from upright to the ground's normal), as boulders do.
- `rest`: `Lowest` (the default) puts the piece's lowest contact on the
  lowest ground under its footprint, so nothing floats; `Plane` sits it on
  the fitted plane, lifted just enough that no contact is below the
  ground.
- `embed`: how deep it sinks after resting, as a share of its size.
- `max_bend`: how far the ground under it may lie from the fitted plane,
  as a share of its size, before the spot is rejected (a log bridging a
  gully, a boulder on a ridge). `None` never rejects.

The piece gives `place()` a `Footprint` in its own space: `contacts` (the
points where it touches flat ground), `extra` (more points sampled only to
find the tilt, such as the two beside a stick's middle) and its `size` in
metres. `place()` then:

1. samples the ground under every contact, extra point and the origin,
   and returns `None` where any is missing;
2. fits a plane `h = a·x + b·z + c` to the contacts and extra points (to
   the origin alone when there are none), and returns `None` where any
   sample lies further from it than `max_bend × size`;
3. tilts the piece by `conform` of the plane's slope;
4. rests it as `rest` says (a piece with no contacts stands on its
   origin), then sinks it by `embed × size`.

Deadwood's old `place()` is `conform` 1 and `Plane`, with its two side
points as `extra`. The deadwood lane (logs 1, stumps 0), mushroom (0)
and the tree grove (0) adopt it.

### Groups

Decided by the user with D3 §7b's Addresses (see D3.md, "Decisions"). Who
defines a group decides how it is handled:

- **A group the asset defines** (a fairy ring or tuft inside `Mushroom`)
  is one copy. Its members are part steps in that copy's address. The
  Scatter still settles each member on the ground at placement time (each
  member's transform gets its own height, with no new specimen). A member
  that can't settle is dropped, and the rest of the group stays. This
  fits the TODO "Mushroom as a whole growth" (mushroom lane).
- **A group the Scatter defines** (pebble clusters in `StoneScatter`) is
  made of ordinary copies. Each member is its own copy and takes its own
  `index` within the candidate cell. No new field is added to the copy
  address; C2 builds the address itself.

Either way, the asset never sees the Ground, and the group's radius counts
in C2's `J`.

## `StoneScatter` (stone lane)

`procgena_stone::StoneScatter::new(&StoneScatterOptions, &ScatterInput)`
spreads stones like a grove spreads species:

- a list of classes (for example boulders, rocks and gravel);
- each class has its own `StoneOptions` (one `StonePool` per class on the
  Bevy side, since a pool holds one `StoneOptions`), a variant count, a
  density per m², a per-copy size range, a spacing, a burial range and a
  `max_slope`.

Each class has its own float lattice with one candidate spot per
`spacing`-wide cell, so its density of spots can't exceed 1 / spacing².
A kept spot holds one stone, or a cluster of `members` stones (a random
count between the two bounds) spread over a disc of `cluster_radius`
around it. Each member is its own copy, numbered by its `index` within
the cell. Every member checks the mask, then `steeper_than`, then
`settle()` with eight contacts on a ring at its variant's ground line.
A member that fails is dropped and the rest of its cluster stays. It
then sinks by its variant's `StonePlacement::embed_depth` times a
per-copy burial draw. Spacing runs greedily in rank order:
- stones of different spots of one class stay `spacing` apart;
- members of one cluster, and stones of different classes, stay clear
  of each other's footprints (classes later in the list give way).

Patches (World value noise, `patchiness` and `patch_size`) are cleared
last, a whole cluster at a time, as the grove clears its glades, so
raising the patchiness only removes stones. The output is each class's
variants (the `StoneOptions` for the pool or the CPU) and the instances
(class, variant, cell, index, scale, local position, footprint radius,
transform). The stone viewer shows it with `--scatter` (key C).
