# D3: stable keys, Terrain and Biome seeds, slot choice

Status: **proposed, waiting for the user.** Written 2026-11-23 from a read
of ARCHITECTURE.md ("Seeds", "Specimen budget", "Masks and placement",
"Loading by chunk", "Edits", "5. World", open questions 4, 5 and 7),
[D1](D1.md), [D2](D2.md) and its spike, `procgena_terrain`'s `hash.rs`,
`graph.rs`, `relief.rs`, `terrain.rs` and `plan.rs`, and
`procgena_biome`. No code was changed and nothing was built.

It settles ARCHITECTURE.md open questions 4 and 5 and the slot choice
under "Specimen budget", and recommends an answer to open question 7 for
F2. It blocks C2 (ids), W0 (Biome and Terrain seeds) and W1 (budget).

## Bottom line

1. **Scatters and Ecotopes are named by a `ChildKey`, not a list
   position.** A key is a short lower-case name (`pines`, `pine_floor`),
   unique within its parent, given in the preset file or by the hook that
   inserts it. The key is the child's identity. A separate display `name`
   can change freely; the key, like a seed key, is frozen.
2. **A child's seed is its parent's seed plus its key**, with one new
   function, `child_seed(parent, kind, key)`, built from the existing
   `derive_seed` and `salt`. The `kind` is a code seed key
   (`"ecotope.child.scatter"`), so a data key such as `hills` can never
   collide with a code key such as `"terrain.relief.hills"`.
3. **Copy ids are structured, not hashed**: region, Ecotope key's salt,
   Scatter key's salt, World lattice cell, index in the cell. Saved edits
   store the key strings, so a renamed or removed key is detected and its
   edits are kept aside and reported, never moved onto other copies.
4. **Terrain gets two seeds: the World seed for its noise, and a region
   seed for its own choices.** Relief, elevation and the region graph keep
   using the World seed unchanged, so every Terrain in a World shares its
   noise and borders keep converging (a Terrain already rebuilds its
   neighbours' relief from their options alone, so this is required, not a
   preference). Region-specific choices take
   `region_seed(world, "terrain.region.local", region)`. The Biome takes
   `region_seed(world, "biome.region.local", region)`. The two are
   siblings, not parent and child, so WorldTerrain derives a Terrain's
   seeds without knowing Biomes.
5. **The rule behind 4: noise sampled at a World position uses a
   World-shared seed; a choice made once per region uses a region seed.**
   Two Biomes on one Terrain preset get different land because they sample
   the shared noise at different places, and different plan choices
   because their region seeds differ. Whether the same rule should also
   cover Scatter placement (no region in a Scatter's placement seed, so
   one Ecotope continuing across a region border has no seam) is the main
   question for the user (question 1). It departs from "Seeds" as
   written; this brief recommends it.
6. **Slot choice: rendezvous hashing**, exactly as D2's spike ran it
   (`hash(key ^ hash(slot))`, highest score wins, ties to the lowest
   slot). It scores a subset directly, nests (a copy whose slot is in the
   subset keeps it), lets a World drop any slot, not just the last, and
   its cost (2.7 ns per copy at `N = 64` on the M1 Max) is negligible
   next to placement. Jump hashing only wins on large whole sets, which
   are rare here.
7. **Open question 7 (recommendation for F2):** drop hook keys from
   `SpecimenId`. Everything that can change a specimen already goes into
   the pool id: the options hash, plus the generator's kind (and, for a
   user generator, its key and version).

## 1. Stable named keys (open question 4)

### The problem today

Under "Seeds", a Scatter's id is its place in its Ecotope's list. A user
hook inserting a Scatter at priority 2 reseeds every Scatter below it,
moves every one of their copies, and orphans every saved edit on them.
The same holds for Ecotopes in a Biome if they are numbered by rule order.
C2 creates copy ids, so the keys must exist first.

### Three keys, kept apart

| Key | Example | Used for | May change? |
|-----|---------|----------|-------------|
| **Identity key** (`ChildKey`) | `pines` | Seeds and copy ids | No: frozen, like seed keys |
| **Preset key** | `"PINE_FOREST_FLOOR"` | Looking up a preset in a catalogue (rule 10) | Yes; renaming a preset doesn't reseed anything |
| **Hook key** (name and version) | `("my_fence", 3)` | The level's cache hash (ARCHITECTURE "Hooks", "Keyed") | Version bumps on every behaviour change |

A hook's version bump must rebuild, never reseed: bumping the version of
"my fence posts" must not move the fence posts. So a hook Scatter has an
identity key for its seed and a hook key for its cache, and the two never
mix.

### The key type

```rust
/// The name of one child (a Scatter in an Ecotope, an Ecotope in a Biome,
/// an asset in a Scatter's mix) within its parent. Unique within the
/// parent, and frozen once worlds are built from it.
#[derive(Clone, Debug, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct ChildKey(Cow<'static, str>);

impl ChildKey {
    /// For built-in presets; panics at compile time on a bad key.
    pub const fn from_static(key: &'static str) -> Self;
    /// For keys read from files or given by hooks.
    pub fn new(key: impl Into<String>) -> Result<Self, KeyError>;
    /// FNV-1a of the bytes: the same `salt` as code seed keys.
    pub fn salt(&self) -> u32;
}
```

- **Form:** `[a-z][a-z0-9_]{0,31}`. No dots: dots belong to code seed keys
  (`<crate>.<area>.<role>`), and copy paths are structured, not strings.
  Lower case only, so `Pines` and `pines` can't both exist.
- **`Cow<'static, str>`, not `&'static str`:** keys come from YAML files
  and from hooks at run time. Interning buys nothing at these counts (a
  few dozen keys per World).
- **Hashed at run time with the same `salt`.** The seed-key rule says code
  keys are hashed at compile time; `salt` is a `const fn`, so data keys
  use the same function at load time and built-in preset keys still hash
  at compile time.
- **Validated by the parent** (`Ecotope::validate`, `Biome::validate`, and
  on deserialise): every key well formed, no two equal, and **no two with
  equal salts** (the same check as the crate registries' test, now at run
  time, since a data key's salt is what goes into the copy id). A clash
  is an error naming both keys.
- **Where it lives:** `procgena_core`, next to the seed functions F2 moves
  there. C2 adds it if F2 hasn't.

### How a child's seed comes from its parent

```rust
// Exists in procgena_terrain::hash; F2 moves them to procgena_core.
const fn salt(key: &str) -> u32;                   // FNV-1a 32
fn derive_seed(seed: u32, salt: u32) -> u32;       // pcg3d([seed, salt, C])[0]
fn seed_for(seed: u32, key: &'static str) -> u32;  // derive_seed(seed, salt(key))

// New.
/// The seed of the child named `key`, of kind `kind`, under `parent`.
fn child_seed(parent: u32, kind: &'static str, key: &ChildKey) -> u32 {
    derive_seed(seed_for(parent, kind), key.salt())
}
```

`kind` is a code seed key, listed in its crate's registry like any other:

| Kind | Crate | Child |
|------|-------|-------|
| `"biome.child.ecotope"` | `procgena_biome` | An Ecotope in a Biome |
| `"ecotope.child.scatter"` | `procgena_ecotope` | A Scatter in an Ecotope |
| `"core.child.asset"` | `procgena_core` (shared placement) | An asset in a Scatter's mix |

The kind level is what keeps data keys apart from code keys: a Scatter
keyed `hills` gets `derive_seed(seed_for(E, "ecotope.child.scatter"),
salt("hills"))`, which shares nothing with `seed_for(W,
"terrain.relief.hills")`. Inside a Scatter, its own random streams
(rank, jitter, per-copy variation) come from code keys under its seed:
`seed_for(scatter_seed, "core.place.rank")` and so on, owned by the
shared placement code. Every kind and stream key keeps the registries'
three-part `<crate>.<area>.<role>` form.

**Mix entries are children too.** A Scatter's mix (which assets, each
one's share) is a list today. If a species is chosen per copy by its
position in that list, adding a species reshuffles the others. So mix
entries get `ChildKey`s as well. How a copy picks its species is C1/C2's
to settle; it should depend on keys, not positions.

### What an Ecotope preset file looks like

Tree's `merge_json` merges objects key by key, replaces arrays whole, and
skips keys the base doesn't have. So a plain list of Scatters can only be
restated whole in a differences file, and a plain map can't gain an
entry. The proposal: Scatters in a map by key, plus an `order` list for
priority.

```yaml
# pine_forest_floor.ecotope.yml
key: PINE_FOREST_FLOOR            # preset key (catalogue lookup)
name: Pine forest floor
group: Forest
default_seed: 7
order: [boulders, pines, logs, ferns, needles]   # priority, highest first
scatters:
  boulders:
    stone: { base: GRANITE_BOULDER, density: 0.002 }
  pines:
    name: Scots pines                # display only; may change
    tree:
      spacing: 4.5
      mix:
        scots_pine: { base: SCOTS_PINE, share: 0.8 }
        dead_pine:  { base: SNAG, share: 0.2 }
  logs:
    deadwood: { base: FALLEN_LOG }
  ferns:
    plant: { base: BRACKEN }
  needles:
    plant: { base: PINE_LITTER }
```

A differences file that adds a Scatter restates only `order` (short) and
adds its entry:

```yaml
base: PINE_FOREST_FLOOR
order: [boulders, pines, logs, mushrooms, ferns, needles]
scatters:
  mushrooms:
    mushroom: { base: FLY_AGARIC }
  pines:
    tree: { spacing: 6.0 }
```

- `order` must name every key exactly once (validation error otherwise).
- In memory the Ecotope holds an ordered `Vec<(ChildKey, ScatterEntry)>`;
  the map-plus-order form is only the file shape.
- This needs F3's merge to accept new keys in keyed maps (today's
  `merge_json` skips them). An alternative is a `priority` number per
  entry (no `order` list, insert with `priority: 35`); see question 4.

A Biome names its Ecotopes the same way, and its rules refer to the keys,
so rules can be reordered or reweighted without reseeding anything:

```yaml
ecotopes:
  pine_floor: { base: PINE_FOREST_FLOOR }
  scree:      { base: SCREE_SLOPE }
rules:
  - { ecotope: pine_floor, landform: [Plain, Bluff], weight: 1.0 }
  - { ecotope: scree, landform: [Scree] }
```

### Inserting a Scatter from a hook

```rust
ecotope.insert_scatter(
    Place::Before(ChildKey::from_static("ferns")),
    ChildKey::new("fence_posts")?,          // identity: seeds and ids
    Box::new(FencePosts::new(/* ... */)),   // carries its hook key and version
)?;
```

Errors: an unknown anchor key, a duplicate key, or a salt clash. Every
other Scatter keeps its seed and the ids of all its candidates.

**What keys do not promise.** Scatters below the new one see one more
mask, so some of their candidates may now be rejected, and with `K_d`
spacing a change can reach `d × R` further (D2 decision 2). Keys keep
ids and seeds stable; survival still follows the masks. An edit on a copy
that no longer survives simply has nothing to act on, and comes back into
force if the copy returns.

### Copy ids

```rust
/// Names one copy anywhere in a World. Stable across loads, chunking,
/// build order and insertion of other Scatters.
pub struct CopyId {
    pub region: RegionId,  // the region whose Biome placed it (u64)
    pub ecotope: u32,      // salt of the Ecotope's ChildKey
    pub scatter: u32,      // salt of the Scatter's ChildKey
    pub cell: IVec2,       // the Scatter's World lattice cell
    pub index: u16,        // point within the cell (0 for one per cell)
}
```

- **Structured, not hashed.** Seeds are 32-bit for the GPU, but edits need
  ids that never collide; this one can't, given the salt check above.
- **The cell is the Scatter's own World lattice cell** (D2), at its own
  cell size, so `i32` covers about a million kilometres at 0.5 m cells.
  `index` is for candidate sources with several points per cell (grass's
  progressive tile, which has 1,024 points per tile today:
  `TILE_POINTS` in `plant/src/shader_model.rs`; the tile grows in size,
  not in points, as density rises).
- **`region` is the region whose Biome's Scatter placed the copy**, not the
  region the point falls in: in a blend zone a Scatter places a little
  past its region's border.
- **Built on its own** (a viewer, a studio tab), a Scatter uses
  `RegionId(0)` and zero salts.
- The GPU never sees a `CopyId`. It sees the Scatter's 32-bit seeds and
  the cell; the CPU rebuilds the id from the same inputs.
- The mix entry is not in the id: it is decided from the id, not part of
  it, so changing species shares never renames a spot.

### Saved edits, renamed and removed keys

Edits on disk store the key strings, not the salts:

```yaml
edits:
  - remove: { region: [3, -2], ecotope: pine_floor, scatter: pines, kind: tree, cell: [8812, -40210] }
  - replace: { region: [3, -2], ecotope: pine_floor, scatter: pines, kind: tree, cell: [8815, -40207], with: { stump: OAK_STUMP } }
```

- **Load** resolves each edit's keys in the World as built. An edit whose
  region, Ecotope or Scatter key no longer exists is **orphaned**: kept in
  the save untouched, reported in the load result, and applied to
  nothing. It is never moved to another copy, and never dropped by the
  library (the game may drop it).
- **Renaming a key** is a removal plus an addition: the new key has a new
  seed, new copies and no edits; the old edits are orphaned. To change
  what the user sees, change `name`. A rename is therefore always a
  deliberate act, and the brief recommends no alias mechanism (question
  2).
- **A removed key that is later reused** gets its old edits back. That is
  right when the same Scatter returns. When the key now means something
  else, the `kind` stored with each edit catches the common case (an edit
  saved on a `tree` now meeting a `stone` Scatter is orphaned and
  reported, not applied).
- **Re-picking a region's Biome** keeps edits whose Ecotope and Scatter
  keys exist in the new Biome: they apply to the same spots. Edits name
  spots, not trees.

## 2. A Terrain id distinct from its Biome's (open question 5)

### What the code does today

| Use | Seed today | Where | Must it match across regions? |
|-----|-----------|-------|-------------------------------|
| Relief layers (swells, hills, mountain mask, ridges) | `seed_for(options.seed, "terrain.relief.*")` with `options.seed` = World seed | `relief.rs` | **Yes.** A Terrain rebuilds each neighbour's `Relief` from `(RegionId, TerrainOptions)` alone for the border blend (`with_edge_targets`), and "Terrains with the same seed share their noise, so alike terrains nearly match already" |
| World elevation E | `seed_for(world, "terrain.elevation.*")` | `elevation.rs` | Yes: one field over the World |
| Region graph sites | `seed_for(world, "terrain.graph.site_*")` | `graph.rs` | Yes: one graph |
| Gully cells | `salt("terrain.gully.cells")`, fixed in every World | `gully.rs` | Yes across a border, so fixed today "whatever the neighbours' seeds" |
| Seam detail | `salt("terrain.seam.detail")`, fixed in every World | `terrain.rs` | Yes across a border, fixed for the same reason |
| Valley wobble | `hash2(river start, 0x9a11_e700 + side)` | `plan.rs` | Per river; not seeded by the World at all, and a hand-picked number (breaks the seed-key rule) |
| `procgena_biome::terrain_seed` | Returns the World seed unchanged | `biome.rs` | Provisional, waiting for this decision |

Every noise layer is sampled at World positions, so all of it must be
World-shared. Nothing today uses a per-region seed. The Biome and the
Terrain "share an id" only in the sense that ARCHITECTURE.md would key
both by region; the code gives both the World seed.

### Proposal

Two streams for the Terrain, one for the Biome, all from the World seed
`W`:

```rust
/// A region's seed for one role. `role` is a code seed key.
fn region_seed(world: u32, role: &'static str, region: RegionId) -> u32 {
    let id = region.0;
    pcg3d([seed_for(world, role), (id >> 32) as u32, id as u32])[0]
}
```

| Stream | Derivation | Used for |
|--------|------------|----------|
| Terrain, shared | `W` itself, through `seed_for(W, "terrain.*")` as today | Relief, elevation, graph |
| Terrain, local | `region_seed(W, "terrain.region.local", region)` | Choices made once per region in its plan that aren't sampled at a World position. **Nothing confirmed uses it yet**: it exists so such choices have a seed that isn't the Biome's. The valley wobble is a candidate (see below) |
| Biome | `region_seed(W, "biome.region.local", region)` | The Biome's per-region choices; the parent of its Ecotopes' seeds (see question 1 for their placement) |

- **The region id needs no fold.** A lattice region's `RegionId` is its
  `RegionKey` packed as `x << 32 | z`; its two halves go into `pcg3d`'s
  two lanes as they are, so distinct regions never share inputs. Two
  regions may still get equal 32-bit seeds by chance; that only
  correlates their per-region choices, and ids never use seeds.
- **Designer polygons need stable region ids too.** "A designer's
  polygons" (World options) must carry a user-given id per region, never
  their list position, for the same reason as open question 4.
- **Siblings, not parent and child.** WorldTerrain and the reference
  stitcher build Terrains from a terrain source with no Biome in sight
  (ARCHITECTURE 5.1). Both region seeds come from `(W, region)` alone, so
  WorldTerrain can derive the Terrain's without knowing about Biomes, and
  changing a region's Biome to another on the same Terrain preset keeps
  its land exactly.
- **The Terrain takes `W`, not a derived seed.** `Biome::terrain_options`
  passes `W` (and `terrain_seed` goes away). The Terrain derives its local
  seed itself in `build`, which already receives the `Region`. Its
  neighbours' reliefs still come from options alone, as today.
- **Different land where it should be, the same noise where it must be.**
  Two Biomes on one Terrain preset sample the same noise at different
  World positions, so their land differs; their plans differ through
  their local seeds; and across their shared border the relief noise is
  the same field, so the seam protocol joins them as it does today. Two
  Worlds differ everywhere through `W`.
- **Gully cells and seam detail stay fixed.** They are fixed today so that
  neighbours with different seeds still agree, and the seam suite tests
  exactly that (`Seeds::Unrelated` in `tests/common/mod.rs`). Inside a
  World every Terrain takes `W`, so `seed_for(W, key)` would agree too
  and give each World its own pattern, but it would make border agreement
  depend on equal seeds and break the unrelated-seed case. Recommended:
  keep them fixed (question 5).
- **The valley wobble needs a keyed seed** (`"terrain.valley.wobble"`) in
  place of `0x9a11_e700`. Whether that seed is the local stream or the
  shared one depends on whether a valley's wobble must match where the
  river crosses a border; that is the terrain owner's call, not D3's.
  Filed as a follow-up.

### The general rule

The Terrain shows the rule that this brief proposes for every level:

- **Noise or anything sampled at a World position takes a World-shared
  seed:** the World seed plus code keys, and (for Ecotopes and Scatters)
  their `ChildKey` path, but no region.
- **A choice made once per region takes a region seed.**

For the Terrain this is not optional: convergence depends on it. For the
Biome's border noise and patch shapes, and for Scatter placement, it is
a choice (question 1).

## 3. Slot choice: rendezvous hashing

### What the spike measured

D2's spike ran both on the CPU and in WGSL with 0 mismatches over
1,048,576 keys. GPU cost per copy, over a baseline that only hashes the
key:

| Mode | N = 4 | N = 16 | N = 64 |
|------|------:|-------:|-------:|
| jump32 | 0.34 ns | 0.54 ns | 0.71 ns |
| rendezvous | 0.21 ns | 0.70 ns | 2.67 ns |
| 4 of 64, jump into the list / rendezvous over it | 0.15 ns | | 0.10 ns |

A 64 m chunk holds about 1,700 trees: 2.67 ns each is under 5 µs. Balance
and moves on the CPU were equal ([slots_prototype.out](d2/slots_prototype.out)).
The low-end and discrete GPU timings D2 still owes should include this
kernel, but nothing here is close to a budget.

### The API needs, one by one

| Need | Jump (`jump32`) | Rendezvous |
|------|-----------------|------------|
| Whole pool, slots `0..N` | `O(log N)`, cheapest | `N` hashes; fine for `N` up to a few hundred |
| Grow or shrink `N` by one at the end | Minimal moves | Minimal moves |
| **Drop one slot that isn't the last** ("slot 7 is an ugly pine") | Impossible: slots are `0..N` | Minimal moves: skip slot 7; only its copies move |
| **A Scatter's or stand's subset** of the `N` slots | Jump into the subset's list: minimal only when the list grows at its end, and the list's order matters | Score the subset's slots directly; order doesn't matter |
| **Subsets nest** | No | Yes: a copy whose whole-pool winner is in the subset keeps it, so turning a subset on moves only the copies that must move |
| Per-pool `N` with World overrides | Fine | Fine |
| Adding or removing pools | Unaffected (each pool has its own slots) | Unaffected |

Mixing the two (jump for whole pools, rendezvous for subsets) would give
a copy a different slot when its Scatter switches a subset on, so one
method must be chosen. Subsets, nesting and dropping any slot all favour
rendezvous, and its extra cost is negligible.

**Recommendation: rendezvous hashing, the spike's exact function.**

```rust
/// The slot, among `slots` (sorted ascending, non-empty), for a copy whose
/// slot key is `key`. Highest score wins; equal scores go to the lower slot.
fn slot(key: u32, slots: &[u32]) -> u32 {
    let mut best = (hash(key ^ hash(slots[0])), slots[0]);
    for &k in &slots[1..] {
        let s = hash(key ^ hash(k));
        if s > best.0 { best = (s, k); }
    }
    best.1
}
```

`hash` is plant's single-lane PCG hash (`common.wesl::hash`), as in the
spike. The spike's subset loop keeps the first of equal scores; sorting
the slots ascending makes that "the lower slot", whatever order a subset
was built in. The rest of this section is new and **not tested by the
spike**:

- **The slot key** is the copy's own 32-bit placement hash mixed with
  the pool: `hash(copy_hash ^ pool_salt)`, where `pool_salt` is the low
  32 bits of the pool id, using the same single-lane `hash` the spike ran
  on the GPU. Copies of different pools at related cells then don't pick
  related slots.
- **`N` is capped**, say at 256 per pool (a validation error above it),
  which bounds the cost at about 10 ns per copy on the M1 Max.
- **Dropped slots** are World data: a pool's `excluded` list next to its
  `N`. Excluding a slot moves only the copies that used it.
- **Stand subsets** ("Local variety from a shared pool"): a stand is a
  cell of a coarse World lattice, its size a Scatter option (say 100 m).
  Each stand picks the top `k` slots by `hash(stand_key ^ hash(slot))`,
  with `stand_key` from the Scatter's seed and the stand cell; each copy
  then picks among those `k`. Growing `N` changes a stand's subset only
  when the new slot enters its top `k`. Stand borders are hard lines; W1
  checks by eye whether that shows, and can blur them by choosing a
  copy's stand from a jittered position. With a World-shared Scatter seed
  (question 1) this is what keeps neighbouring regions from all picking
  the same subset; "hash its own id" alone would not.
- **A World override names a pool by a path**, because the options hash
  isn't something a person can write or keep stable:
  `budgets: { temperate_forest/pine_floor/pines/scots_pine: 12 }` (Biome
  preset key, Ecotope key, Scatter key, mix key). Several paths can lead
  to one pool (equal options); then the pool takes the largest `N`
  named, with a warning. W1 settles the details.

## 4. Hook keys in the specimen id (open question 7)

This falls out of section 1, so here is a recommendation; ROADMAP gives
the decision to F2.

- An Asset has no hooks. A hook that changes an asset's options (a Biome
  making its pines shorter) changes the options hash, so it already makes
  a new pool.
- An output hook changes copies (transform, tint), never specimens.
- What the options hash can't see is **code**: a user's own generator
  behind the `Scatter` trait or `MeshScatter`. Its pool must change when
  its code does.

**Recommendation:** `SpecimenId = hash(W, pool id, slot)`, with
`pool id = hash(generator kind, options hash)`. A built-in generator's
kind is a code seed key (`"tree.generator.kind"`); a user generator's kind is
its hook key, name and version. No separate "hook keys" field. Putting
the kind in also keeps a tree pool and a stone pool apart should their
options hashes ever collide.

## 5. Conflicts with ARCHITECTURE.md

Not edited here; each needs the user's decision first.

1. **"Seeds", second bullet:** "its region for a Biome and its Terrain, its
   place in the list for an Ecotope's Scatters. So two Biomes that use
   the same Terrain preset still get different land." The list position
   becomes a `ChildKey`. The Terrain's noise is not seeded by its region
   (it can't be, or borders stop converging); its land differs by World
   position, and only its per-region choices use a region seed.
2. **"Seeds", the chain:** if question 1 is answered "shared", Scatter and
   Ecotope placement seeds skip the region, so the seed tree is no longer
   one chain. "Worked out from the World seed and its id alone" still
   holds.
3. **"Specimen budget", "Local variety":** "hashes its own id to pick a
   small subset" becomes stand subsets from a coarse World lattice
   (section 3). The candidates list becomes the decision for rendezvous.
4. **"Specimen budget" and rule 3:** "and any hook keys" goes, if F2 takes
   section 4's recommendation.
5. **"Seeds", the seed-key rule:** it covers code keys hashed at compile
   time. It needs a line for data keys: `ChildKey`s hashed at load time
   with the same `salt`, always under a code `kind` key.

## 7. Questions for the user

1. **Should Scatter placement seeds include the region?**
   - **Shared (recommended):** a Scatter's placement seed is
     `child_seed(child_seed(W, "biome.child.ecotope", ecotope),
     "ecotope.child.scatter", scatter)`, with no region. The lattice is
     World-anchored, so regions still look different; where the same
     Ecotope continues across a region border (one forest Biome over many
     regions, the common case) the candidates are identical on both sides
     and the forest has no seam. It matches how the Terrain already
     shares its noise. Biome border noise and patch shapes would follow
     the same rule. Copy ids still carry the region. Its costs:
     - **Ownership at a shared border is unsettled.** Where two regions
       place the same Ecotope, both would place the same candidate, so
       one must own it, and `CopyId.region` ("the region whose Biome
       placed it") needs a rule there. A candidate rule is the region
       holding the cell's corner (`RegionGraph::region_at`), but how it
       fits blend zones is B1 and C3's to check.
     - **Unrelated Biomes that reuse a key path share placement seeds**
       World-wide: a `floor`/`trees` in a temperate Biome and in a boreal
       one rank their candidates identically. Their copies still differ
       (other species, density, spacing), and in a blend zone the shared
       ranks act as a common dither, but the correlation is real. Adding
       the Biome preset key to the path would remove it, at the price of
       a seam wherever two different Biomes meet (which the protocol
       blends anyway).
   - **Chained:** the seed goes through the region's Biome seed, as
     "Seeds" reads today. Simpler to state, but every region border is a
     seam in every Scatter, which the Ecotope border protocol then has to
     blend even between identical Ecotopes.
2. **Keys are frozen, with no rename aliases?** Recommended: yes.
   Changing `name` is free; changing a key orphans its edits, which are
   kept and reported. An alias list (`previous_keys`) is possible later,
   but it would have to keep seeding from the old key, which is the same
   as never renaming.
3. **Rendezvous hashing for slots, with a cap on `N` (256) and per-pool
   excluded slots?** Recommended: yes.
4. **Ecotope files: a map of Scatters plus an `order` list, or a map with
   a `priority` number per entry?** Recommended: `order`. It shows the
   stack in one line and can't tie; the cost is restating it when a
   differences file adds a Scatter.
5. **Gully cells and seam detail: keep them fixed in every World, or move
   them to `seed_for(W, key)`?** Recommended: keep them fixed. Moving
   them gives each World its own pattern, but makes border agreement
   depend on equal seeds and breaks the seam suite's unrelated-seed case
   (`Seeds::Unrelated`).
6. **Open question 7:** drop hook keys from `SpecimenId`, putting the
   generator kind (and a user generator's key and version) into the pool
   id? Recommended: yes, for F2 to confirm.

## Follow-ups found on the way

- **Valley wobble** in `plan.rs` seeds from a hand-picked
  `0x9a11_e700 + side` hashed with the river's start point, so it does not
  depend on the World seed and breaks the seed-key rule. It needs a keyed
  seed (terrain owner's call whether local or shared).
- **`TerrainOptions::seed`'s doc** says "Give neighbouring terrains the
  same seed". After W0 that is always true inside a World; F3's rename to
  `default_seed` should reword it.

## Shortcuts in this brief

- No code was run. The stand subsets, the slot key's pool mixing, the
  `N` cap's cost and the `order` merge are proposals; only the slot
  function itself was tested (by D2's spike, on one GPU).
- The collision check for data keys is argued, not measured: FNV-1a over
  a few dozen short keys per parent clashes with negligible probability,
  and validation catches it when it does.

  on which region owns each copy (under question 1's shared option) is

  not checked against blend zones.

  names (`procgena_ecotope`) that don't exist yet.
